## 2. 文件所有权与并行边界

- `src/shared/subject-contract.ts`：仅 backend 可改；改动前先确认对前端是**增量兼容**（新增字段，不破坏既有字段）。
- `src/components/**`、`src/lib/**`：仅 frontend。
- `src/server/**`：仅 backend；`src/app/**`、根配置、`package.json` 本轮不动。
- `docs/ui-design.md`：仅 designer；`docs/qa-report-round3.md`：仅 qa。
- 任何人发现需要动别人文件：停下来报告 Lead，由 Lead 协调，不自行越界。

## 3. 协作规则

1. 所有成员开工前必读：`/home/viiling/项目开发约定规则.md`、`AGENTS.md`、`docs/round3-requirements.md`。
2. 不安装新依赖；不 `pnpm add`；不提交 GitHub（本轮不提交，无需 PAT）。
3. 端口：开发/验收统一 8004；**同一时间只允许一个成员占用 dev 服务器**，用完必须结束进程。最终验收由 QA 启动。
4. 不碰 `dump-db/`、`prisma/*.db`、`.cache/`、`.env.local`；不伪造测试结果。
5. 完成标准：交付「改了什么 + 跑了什么验证 + 已知风险」三段话，不贴大段代码。
6. 测试真实数据：涉及封面缓存/接口的改动必须在真实缓存库上验证；UI 必须看真实浏览器截图。

## 4. 执行顺序

1. **S1 设计**：designer 产出面板布局/尺寸/断点/状态规格 → Lead 审核。
2. **S2 后端**：backend 支持原图地址并完成缓存无损升级 → 报告契约变化。
3. **S3 前端**：frontend 按设计稿实现（依赖 S2 的契约）→ 自测。
4. **S4 独立测试**：qa 起 8004，逐条验收 + 回归 + 截图 + 性能观测 → 报告。
5. **S5 修复回路**：QA 缺陷单点回对应 owner，修完重测；Lead 不做代码修改。
6. **S6 交付**：Lead 汇总业务影响、资源变化、验收结论，向用户汇报（本轮不提交）。
